# User help (docs/user/)

The task help is Sphinx RST under `docs/user/source/`, imported from
gitlab.com/ccp4i2/rstdocs (which stays the Qt interface's help). Figures are
screenshots of the running app, regenerated by script, never pasted by hand.

This skill routes to the tooling and holds the judgement it cannot express.
The mechanics are in `docs/user/README.md`; do not copy them here.

## Where the work goes

Pull requests for this work, pages and the fixes they turn up alike, target
the **`docs-integration`** branch, not `django`: it reaches `django` as one
pull request, so it does not interleave with other work being gathered for
an alpha. Branch each piece from `docs-integration`. CI runs on every pull
request whatever its base.

## Converting a page: the order that works

1. **Read the task's interface first**, `client/.../task-interfaces/<task>.tsx`,
   not the old page. The new layout (tabs, folders, labels) decides the
   page's sections; the Qt page's "Basic/Advanced options" usually no longer
   exist. Labels in the `.tsx` (`guiLabel`) are what callouts are keyed on.
2. **Choose the example data for the science, not convenience.** It must
   show the task doing its job: parrot needed a partial model with real NCS
   (1h1s, CDK2 without its cyclins). A dataset that makes the report say
   something odd ("9 copies") is the wrong one, however handy. Fetch from
   PDBe / PDB-REDO in the scenario; do not add to `demo_data` (it ships with
   CCP4). The URL helpers in `server/ccp4i2/tests/i2run/urls.py` are the
   reference.
3. **Write the scenario as a script** (`tools/scenario_<task>.py`) that runs
   i2run into a scratch `CCP4I2_HOME` and ends with an unrun clone for the
   input figures. Chain jobs with `fileUse=<task>[-1].<PARAM>`, so the job
   list and pickers show a real history.
4. **Look at every figure before writing a word.** Screenshots find bugs:
   parrot's first capture turned up a wrong solvent estimate (#689), UUID
   annotations (#692), raw `<sub>` in a legend, a red field the server
   thought fine, and a typo. Fix what is small in the same PR; file the rest.
5. **Keep the original prose where it is still true.** The Qt pages hold
   good crystallographic advice. Change what describes the Qt window, what
   the new interface does differently, and numbers the new menus changed.
6. Run `tools/compress_images.py` on new figures; build with
   `tools/build.sh` (the warnings ratchet).

## Traps

- **Never point anything at a live home.** The scenario refuses
  `~/.ccp4i2*`; run the app for capture on ports of its own (other sessions
  hold 3000/3001 and sometimes 3200/3201, on the live database).
- **Developer mode starts on** in every page load (`useState(true)`); the
  capture turns it off through the View menu. A capture showing *Def XML* or
  *Job container* tabs has skipped that.
- **Reports cache** as `report_xml.xml` in the job directory; after changing
  a report class, delete it and restart Django (`--noreload`) to see the change.
- **Graph titles cannot contain spaces**: the loggraph header is
  whitespace-split, so "Fcorrel (work)" becomes two series. Use underscores.
- **Chart titles are drawn on canvas**, so they are not DOM text; a callout
  on a plot targets its "Plot" selector label instead.
- **An exception thrown inside a page-side timer never rejects**: the capture
  hangs. Keep page steps synchronous and sleep on the Node side.
- **JPEG is wrong for screenshots**: 256-colour PNG is smaller and sharper.
- **Make the scenario check its own story.** A run can succeed and show
  nothing: SubstituteLigand "fitted" no ligand because the atom selection
  `not (NUT or HOH)` matched nothing and left the parent's ligand in the
  site. The selection language wants `not (NUT) and not (HOH)`; a name that
  matches nothing is accepted silently. Assert the outcome (the ligand is in
  the output model) and, where the truth is known, measure against it.
- **Heavy reports need longer to settle** (`"settle": 30000` in the shot);
  "Nothing to click labelled View" on a report page is usually that.

## Writing a page for a task that has none

Draft from the task's own sources: its `def.xml` (parameters, defaults,
menus), its interface `.tsx` (what the user sees), its wrapper (what it
actually passes to the program), its report class (what the results show)
and the program's own documentation. Say what the task is for and when to
choose it over its neighbours in the chooser category before describing any
field. A drafted page is not reviewed science: say so in the PR, and have a
crystallographer who knows the program read it.
