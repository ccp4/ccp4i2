# User help (docs/user/)

The task help is Sphinx RST under `docs/user/source/`, imported from
gitlab.com/ccp4i2/rstdocs (which stays the Qt interface's help). Figures are
screenshots of the running app, regenerated by script, never pasted by hand.

This skill routes to the tooling and holds the judgement it cannot express.
The mechanics are in `docs/user/README.md`; the traps, by stage, are in
[traps.md](traps.md); the brief for a page-drafting subagent is
[subagent-brief.md](subagent-brief.md).

## Where the truth lives

| What | Where |
|---|---|
| How to build, run the app, capture | `docs/user/README.md` |
| Progress per chooser task (current / draft / Qt / none / stale) | `python3 docs/user/tools/status.py`; `status.rst` each build |
| What is left, by chooser category (to choose a route) | `python3 docs/user/tools/status.py todo` |
| Everything about one task, from source | `python3 docs/user/tools/taskcard.py <task>` |
| What a page shows, and from which project | its `shots.json`; the scenario it names |
| Page directories not named after their task; pages for several tasks | `ALIASES` in `tools/status.py`; `"task"` / `"tasks"` in `shots.json` |
| Whether a page still matches its task | `"sources"` in `shots.json`; `tools/stamp.py check` |
| The scenarios' jobs and files | `manage.py list_jobs <project>`; `list_files --project P --job N --format json` |
| A good model page | `tasks/pairef/`, `tasks/phaser_mr_phil/` (shared page), `tasks/import_files/` |

## The tools

| Tool | For |
|---|---|
| `tools/devserver.sh start\|stop\|restart [django\|next\|all]\|status\|clear-reports P N...` | the app against the scratch home (Django 3421, Next 3420) |
| `tools/scenario_*.py`, `scenario_common.py` | building a project by i2run; `clone_last`, `output_file_id` |

## A route, in order

Work goes in **routes**: a set of related tasks illustrated from one project,
each route a pull request. Routes stack on each other while CI runs; a stack
is flattened into one pull request to `django` so it takes one CI cycle
(retargeting re-runs CI since #705). `django` is PR-only.

1. **Choose the route and its data for the science.** The project must show
   each task doing its job and answering a real question (MDM2 with its
   uncut data for PAIREF; a distant Chainsaw model for the Phaser steps). Use
   `demo_data` or fetch from PDBe/PDB-REDO in the scenario; never add to
   `demo_data`. Run `taskcard.py` on each task first.
2. **Write the scenario** (`tools/scenario_<route>.py`): i2run into the
   scratch `CCP4I2_HOME`, files passed by `fileOut=`/`fileIn=` (also inside
   list items: `pdbItemList/structure/fileOut=...`), the outcome asserted,
   an unrun clone of each task at the end. Run scenarios one at a time: the
   project's database and job numbers are shared.
3. **Read the results before anything else**: the program XML and logs, not
   the pictures. The numbers the page will quote come from here, checked
   (gemmi, the program's own files) before they are written.
4. **Outline every page** (`"outline": true` shots on the clone's interface
   and the run's report). This finds the sections, labels and values, and
   most of the defects: raw parameter names, unannotated outputs, empty or
   failed reports.
5. **Fix what the outlines show**, centrally, with a test each (a report in
   a unit test, an annotation in the i2run test). Restart Django and clear
   the cached reports after server changes.
6. **Write `shots.json` and capture**, then look at every picture once. A
   picture shows what an outline cannot: layout, overflow, a drawing that is
   text, a badge in the wrong place.
7. **Write the page** (see *Write the judgement down*), compress the
   figures, build (`tools/build.sh`, the warnings ratchet), and **stamp**
   (`tools/stamp.py stamp <page>`): a stamp says someone checked the page
   against its sources. Restamp only after reading `stamp.py diff`.
8. **Before the route's PR**: unit tests in the CCP4-free venv, api/unit,
   tsc and vitest, the i2run tests the fixes touch. No Claude attribution in
   commits or PR bodies.

## Dividing the work with subagents

The main session owns everything shared: the scenarios (one database, one
numbering), the dev servers, all server and client fixes, and the
verification of every crystallographic claim. Once a route's jobs exist,
drafting pages is independent per task and can be fanned out: each subagent
gets a brief ([subagent-brief.md](subagent-brief.md)) with the task card, the
job numbers, the outlines and the numbers already checked, writes the page
and its `shots.json`, captures and looks at the pictures, and **reports
defects instead of fixing them**. Fixes made in parallel collide, and a
claim a subagent drew from a picture has not been checked. A cheaper model
can draft; the main session reviews every page before it is stamped.

The first trial (five utility tasks, #715) cost each Sonnet subagent 80-130k
tokens and five to eight minutes, and its reports found nine real defects
the outlines had not. Expect the review to be real work: read each page's
"not in the checked facts" list, check or cut those claims, then fix the
defects, restart Django, clear the reports and recapture **one page at a
time** (`capture.mjs` now queues on a lock, so parallel captures wait
rather than contend). A field relabelled by a fix breaks the shots that
name it (`"field"` matches the whole label): update them before recapturing.

The prompt is short: "Read `.claude/skills/user-docs/subagent-brief.md` and
follow it", then the route's specifics; the brief holds the rest.

## Write the judgement down

Every page says, in plain words, what an experienced user would know and a
program cannot see: when to use the task and when not; the numbers that
mean success or failure (Phaser TFZ and LLG, R-free against R, PAIREF's
change in R-free and how many free reflections it rests on); the traps
(reuse the free set a model was refined against; a selection that matches
nothing is accepted silently); and what to do next. The scenarios are the
same knowledge as executable recipes, asserting their own outcome. Both are
meant to outlive this interface: they are the seed of LLM-agnostic
knowledge for agentic CCP4 (Martin, 2026-09-30).

Every number on a page comes from the run, checked; every claim about what
a task does comes from its code or its program's documentation, not from
memory. Keep the old page's prose where it is still true.

## Writing a page for a task that has none

Draft from the task's own sources (`taskcard.py`, its wrapper, its report
class) and the program's documentation. Say what the task is for and when
to choose it over its neighbours in the chooser before describing any
field. A drafted page is not reviewed science: say so in the PR, and have a
crystallographer who knows the program read it. Tasks that cannot be run
from a scenario (interactive programs, licensed or remote services; see
traps.md) are documented from an unrun job's interface and prose only.
